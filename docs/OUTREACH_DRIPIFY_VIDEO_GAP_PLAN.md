# Outreach gap plan from Dripify's quick-start video

Date: 2026-09-29. Scope: [Dripify's 12:34 quick-start video](https://www.youtube.com/watch?v=dnZTzJOelOo), published 2025-02-26, compared with the current Unravler repository. This is a code-and-video audit, not a live LinkedIn, email-provider, proxy, or production verification. The video is a workflow reference, not a specification or evidence for performance and account-safety claims.

## Delivery order

### P0 — Release truth, permissions, and pilot proof

1. Keep **production** `OUTREACH_LIVE_ACTIONS_ENABLED=false` until product/legal go-or-no-go and pilot evidence. After approval, use a separate isolated pilot deployment or tightly allowlisted, time-bounded activation for one consented sender with a purchased proxy; do not require a production rollout to obtain the evidence. LinkedIn's [User Agreement](https://www.linkedin.com/legal/user-agreement) prohibits unauthorized automated access, messaging, likes, comments, and scraping. Caps, jitter, and residential proxies do not establish compliance or guarantee account safety.
2. Build a route-by-route authorization matrix for **every** outreach mutation: campaigns, sequences, leads, senders, inbox replies/sync/reminders/snippets/tags, Engage, voice, styles, swipe, prompts, billing, mailboxes, reconciliation, and integrations. Fill missing checks without duplicating existing ones. Use permissions appropriate to viewing, editing, launching, billing, and secrets; refine broad integration permissions where needed. Enforce workspace/assignee boundaries and test viewer-denied, cross-workspace, role-change, and revoked-member cases. Existing membership checks alone are not action authorization.
3. Fix production Compose's explicit environment mapping for `OUTREACH_LIVE_ACTIONS_ENABLED` *without enabling it*. `backend/.env` passed with `docker compose --env-file` does not inject an unmapped variable into containers. Add a deployment assertion that every release flag expected by API/worker/beat is present with its intended value.
4. Replace the campaign-detail acceptance/reply percentages derived from unrelated stage counts with a clear “not available” state until the actual sent/accepted/replied event denominators are defined. Establish a canonical action-outcome record and link existing task, inbox, and outbox records before building a detailed timeline or new metrics; do not assume the current outbox is a complete event ledger.
5. In the isolated/allowlisted pilot after approval, run a bounded journey: invoice/entitlement grant → country-matched dedicated IP lease → sender verification → import → campaign preflight → approved dispatch → reply capture → follow-up halt → expiry pause. Test failed proxy, 429/checkpoint, lost response, duplicate job, missing mailbox, sender disconnect, and paid-term expiry. Record observed results; do not infer readiness from mock tests.

**Exit:** no unauthorized role can mutate outreach state; production live actions stay disabled until a separate rollout decision; misleading rates are removed; one approved pilot journey and failure matrix are recorded and reproducible.

### P1 — Make the first campaign genuinely usable

1. Add pasted LinkedIn profile URLs as a manual lead source, alongside CSV. Parse only URL/vanity information, require a user-supplied name when absent, and never invent profile details. First deliver preview/validation with row-level error reasons, source/consent metadata, custom fields, dedupe, DNC, and import result counts. The current CSV route is synchronous; add queued import progress/cancellation only after volume justifies a job, checkpoints, idempotent batch writes, and defined cancel semantics. Do not silently scrape search results or imply the six disabled source tiles work.
2. Once the action-outcome record has provenance, add an **internal, workspace-scoped, paginated** lead-activity API that combines action outcomes, inbound replies, state changes, notes, and campaign history with retention rules. The current gated `/leads/{lead_id}/history` integration endpoint is only a capped, sanitized task projection; it is not the complete internal timeline. Show each lead's current sequence node, next eligible action, sender, last confirmed outcome, pause reason, and activity in campaign and lead views.
3. Add a launch checklist that names exactly why a campaign is blocked: entitlement, healthy sender, country-matched proxy, mailbox for email nodes, supported node, lead count, schedule, and any warm-up gate. Preview branch paths and message variables; distinguish draft, armed, active, paused, uncertain, completed.
4. Make pause-on-reply and resume observable. Inbound LinkedIn/email replies should stop queued follow-ups idempotently; manual resume must re-check entitlement, suppression, sender health, and sequence position. Never re-send a task with an uncertain external outcome automatically.

**Exit:** a pilot user can import their own lead data, build a supported sequence, understand every blocker and each lead's position, and confirm replies stop future touches.

### P2 — Prove value with reporting, email, and integrations

1. Base the funnel on deduplicated, provenance-linked action/inbound records. Define denominators and time windows for attempted, confirmed sent, accepted, replied, bounced, and opted out. Replace hard-coded zero delivery with `unknown` until provider evidence exists. Provide campaign and sender filters (sender attribution from task/account records) and CSV export; defer per-member filters until ownership exists. Do not attribute a reply to Engage without a causal link.
2. Pilot Gmail/Microsoft connection, one-to-one send, reply/bounce/opt-out sync, token revocation, and uncertain-send recovery with consented recipients. Current feature flags are global environment variables: use an isolated pilot deployment first, or implement workspace-level allowlists checked by API **and** workers before enabling any pilot workspace in shared production. Reflect the gate consistently in the builder and launch validation.
3. Pilot outbound webhooks/Slack/Sheets/HubSpot with event identity, scoped keys, retry/dead-letter inspection, replay permission, and per-destination status. Require signed delivery for outbound webhooks and validate each other destination's own authentication/retry contract. Assert no secrets or message bodies leak to notifications. The integration code exists; it is not a production promise while its release gate is off.
4. Add sender/campaign ownership and per-member views only after P0 RBAC; make role/assignee changes auditable. Then add per-member analytics. Show template usage/performance only when backed by real event data.

**Exit:** dashboard numbers trace to recorded events, the mailbox/integration pilot survives duplicate and delayed events, and team access cannot cross authorized boundaries.

### P3 — Optional parity after evidence and policy review

- Evaluate search/Sales Navigator/event/group/connection acquisition only with a permitted data-access path and clear user authorization. If unavailable, keep CSV and user-supplied URLs; do not create a hidden scraping dependency.
- For video-only nodes such as InMail, Follow, Endorse, and invite withdrawal, decide independently between supported API, explicit human task, or removing the tile. Each live node needs verified provider behavior, idempotency, post-action reconciliation, caps, failure handling, and tests before the capability catalog can mark it live.
- Add imported-name normalization as an **editable preview** with fallback to the original name, not an unreviewed transformation. A style/emoji scrubber is low priority compared with verified lead intake and outcome tracking.

## Definition of done for every slice

Backend authorization and idempotency tests; frontend disabled/loading/error/empty states; worker retry and unknown-result tests; accessibility/keyboard checks; real-provider pilot evidence where applicable; truthful release-flag and marketing copy; audit logs with redacted secrets. No feature is “available” merely because a button, route, model field, or mock test exists.
