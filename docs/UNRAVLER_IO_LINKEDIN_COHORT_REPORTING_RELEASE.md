## Recorded evidence contract

The read-only [evaluator](../outreach/core/linkedin_reporting.py) uses `outreach_intents`, task metadata and the existing event outbox. It opens no credentials, calls no provider, writes no domain record and issues no permission.

- A send requires an original canonical intent identity, scalar campaign/lead/sender/enrollment/node/operation references, valid sequence version, executed status, the original attempt ID/owner and matching claim, `provider_accepted`, and action-specific `invite_sent` or `message_sent`. Native `created_at <= possible_submission_at <= completed_at <= as_of` is required. Task `updated_at`, lead flags, creation dates and human assertions cannot substitute for original confirmation evidence.
- The lifetime minimum confirmation time is chosen **before** the selected period. The key is `(campaign_id, lead_id, sender_id, action_kind)`. Follow-ups and reenrollment under the same key do not reset that cohort. Different lead records for the same person remain separate; this is not canonical-person deduplication or proof of the first actual send. Denominators survive current lead deletion or reassignment.
- An associated acceptance/reply requires a matching stored LinkedIn outbox type and scalar campaign/lead/sender references, consistent envelope ID/type/workspace/time and native `occurred_at` between the first confirmation and `min(as_of, confirmation + 30 days)`. BSON millisecond precision is normalized when checking the envelope's ISO timestamp. Duplicate observations count once per cohort key. Email events and lead `has_replied`/`replied_at` do not establish a LinkedIn reply.
- These dates represent original local send confirmation and stored observation time. Outbox events lack enrollment/message binding; an observed connection can already exist, and one connection-observation writer records before its lead update succeeds. The association is not causal conversion, delivery, authenticated provider evidence or the actual provider reply/acceptance time. Missing retained observations mean zero matching recorded observations, not proof of no reply/acceptance. Recent 30-day windows remain open; matured/open denominator counts are exposed.
- Historical mock adapters can record the same `invite_sent`/`message_sent` status strings, and the intent attempt does not retain an independent mock/transport-source discriminator. This evaluator cannot authenticate such records as real LinkedIn transport. Recorded acceptance labels describe stored status only; source-authenticated transport evidence and migration remain separate work.
- Selected legacy, incomplete, human-reviewed or uncertain history is reported separately. Non-null review markers remain unproven even if their source is missing or malformed; only a recognized human source increments the separate human counter. Missing/array channel labels are unverified. Known usable counts can remain visible with `status=partial`, but percentages are null. A recorded empty denominator is zero with a null percentage. Capacity/read/deadline failure yields `status=unavailable` and null counts/rates.

Reads use exact scalar workspace and selected campaign/sender scope, metadata projections and a ten-second caller deadline. Limits are 10,000 selected intents, 10,000 task records and 20,000 matching observations, each with overflow detection. The resolution marker is projected as a Mongo type plus source, excluding private review notes. These are sequential reads, not a database snapshot, retained-history completeness guarantee or server cancellation guarantee. A fixed `as_of` is a timestamp cutoff; it cannot freeze concurrent database changes.

## API, screen and CSV

The existing request/message `sent`, outcome, `denominator` and percentage aliases now refer to the same recorded cohort; `cohort` exposes the corresponding detailed fields. Period task-update and lead-observation counts are retained separately in `period_activity` and the daily chart. That activity can contain different cohorts, legacy repairs and cross-channel lead reply flags; it is not used to calculate conversion percentages. Future dates are excluded from request/message period activity and the daily task/lead counts at the captured report time. Manual Engage aggregate dates retain their earlier behavior and are outside this correction.

The screen displays period activity separately from associated observations and labels the 30-day window. Loading, partial, unavailable and valid empty states remain distinct. Older API responses cannot restore legacy percentages. CSV retains daily activity columns and appends the cohort basis, outcome basis, status, UTC bounds, window and counts/rates. Cohort summary fields are explicitly labelled `selected_period_summary_repeated_on_each_daily_row`; they must not be summed across daily rows. There are no new collections, indexes, migrations or runtime defaults.
