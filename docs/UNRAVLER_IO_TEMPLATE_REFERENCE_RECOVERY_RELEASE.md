# Unravler.io v2.77 — Same-tab template-save recovery

Updated: 2026-10-17 IST. Bounded local frontend change, uncommitted and undeployed. This extends [recoverable template saves](UNRAVLER_IO_TEMPLATE_SAVE_RECOVERY_RELEASE.md); backend/API/database contracts are unchanged. Revisioned editing and sharing remain subsequent work.

An uncertain template save now retains its original reference across reload and wizard departure within the same browser tab. On reopening, Save remains blocked until an explicit **Check save status** reviews the current server context. Recovery submits only the matching original status GET; it never posts the graph again or allocates another request ID automatically. Exact HTTP200 receipt validation still confirms recorded historical creation, not current template existence or execution authority.

The versioned sessionStorage envelope contains at most10 references and8192 UTF-16 code units of serialized data. Each exact five-field locator contains contract version, workspace, opaque original actor/UID/workspace scope digest, request UUID and input hash. No token, raw UID, template name/description, graph, compiled content or provider credential is stored. Locators/hashes remain correlatable data, not anonymized records or authority grants. Malformed envelopes, duplicate scopes/UUIDs, invalid types, overflow, blocked reads/writes and failed write verification hold without eviction or destructive cleanup.

Every template POST synchronously rereads, conditionally appends and verifies storage after all context/preparation/hash awaits and before transport. An unresolved same-scope original prevents another request, including competing hooks within the same document. This is not cross-tab locking or coordination with arbitrary same-origin scripts. Initial nonempty storage blocks saves; foreign references remain retained. Only an exact fresh server context can permit a deliberate save for a scope with no matching reference. Both workspace and digest must match before a status GET. A foreign in-memory original lost through external storage clearing is restored with normal bounded admission before another scope can unlock; failed restoration holds.

Only a matching current receipt permits conditional removal of its original locator. A newer same-scope reference is never removed by an older confirmation; cleanup rereads before unlocking. Cleanup failure retains a hold, even when creation was confirmed. Status404/errors remain unconfirmed, including the write-ahead crash window where storage succeeded but POST never started. There is no cancellation/tombstone protocol to prove an absent request can be discarded. No automatic reset, eviction, POST replay or fresh UUID bypass is supplied.

SessionStorage can survive reload and same-tab navigation; clearing storage, tab closure, browser loss, duplicated-tab copies, raw script changes and browser-specific restoration remain limits. This is not durable browser-wide operation history, cross-tab exactly-once behavior or authenticated restore completeness. Already submitted requests cannot be recalled. Backend current UID/role/erasure authority, historical receipt retention, and separate preparatory draft/sequence-write limits remain as documented in v2.76. Ordinary editor autosave, template editing/sharing/deletion receipts, team/sender governance and execution flags are unchanged.
