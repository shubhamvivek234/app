# Unravler.io v2.76 — Recoverable custom-template saves

Updated: 2026-10-16 IST. Bounded local implementation, uncommitted and undeployed. This follows [reviewed template deletion](UNRAVLER_IO_TEMPLATE_GOVERNANCE_RELEASE.md) and [gallery configuration](UNRAVLER_IO_TEMPLATE_GALLERY_RELEASE.md). Revisioned editing, sharing and wider template ownership remain separate.

## Behavior

The wizard's **Save as template** uses an original request reference. One database transaction creates the template at revision1 and records a minimal historical creation receipt. An identical original request returns that receipt; different content using the same reference conflicts. A completed original request never recreates a template deleted later, and recovery does not depend on the current compiler or current template contents.

An uncertain response holds the save. **Check save status** explicitly reads its original reference without posting the graph again. Only HTTP200 with the exact matching receipt confirms creation. Missing status, transport errors,403/409/503,201/202, malformed bodies or mismatched input/scope remain unconfirmed. There is no automatic POST retry or automatic fresh request ID after an unknown outcome. A confirmed creation allows another deliberate new save; separate request IDs can intentionally create separate templates with the same content.

The new routes are `GET /sequences/template-saves/context`, `POST /sequences/template-saves` and `GET /sequences/template-saves/{request_id}` with the original workspace/scope query. They cannot fall through the older `/sequences/templates` POST handler. The older guarded POST remains available for compatibility and remains non-idempotent; its consumers and old API writers require their existing drained rollout. Existing reviewed deletion and gallery configuration contracts are preserved.

## Input and durable record

The browser freezes the exact JSON serialization of name, description, nodes, edges and visual tree, then hashes its UTF-8 bytes with SHA256. The server hashes those same received `content_json` bytes and requires the captured digest. Whitespace, Unicode encoding and numeric serialization belong to this original input contract; the protocol does not assume Python canonical JSON equals browser serialization. Accepted input is at most1MB of UTF-8, after receipt/encoding. This is not an HTTP-ingress memory bound; normal graph/semantic/compiler and full stored-BSON bounds also apply.

The scope binds the admitted scalar original actor, Firebase UID and resolved workspace. The deterministic receipt `_id` binds that scope and request UUID. `outreach_template_saves` uses MongoDB's automatic unique `_id` index, noTTL and no additional index or production migration. Receipts contain bounded workspace/actor/request references, the original input hash, template ID/revision/native-identity/full-record hashes and native UTC-millisecond BSON creation time. They contain no template name, description, graph, compiled content, raw Firebase UID or provider credentials. References and digests can remain personal or correlatable data; this is not an anonymization claim.

Strict stored receipt keys, scalar string types, integer contract/revision, deterministic key/scope and native timestamp shape are validated. BSON Code values cannot masquerade as receipt strings. The transaction rereads the inserted template, requires its actual BSON review to match the prepared record, and builds the receipt from that stored review. It rereads the inserted receipt and requires exact encoded equality before confirmation. Malformed or colliding records hold without replacement. This is application-recorded evidence, not a signed external receipt or independent authentication of raw database writers.

## Authority, concurrency and erasure

First saves, original retries and status reads all use the shared workspace snapshot/majority transaction. Current original-UID/native-user/member-or-owner creation authority and erasure checks use the existing authority-counter fences. Status GET therefore writes authority/guard counters; it does not modify template contents or authorize execution. Read-only context metadata alone grants no mutation permission.

Creation and its receipt commit together. Same-reference concurrent calls produce one template/receipt; conflicting input admits only one original. Definitely aborted database retries retain the prepared native/public identity. Unknown commit acknowledgements remain held and are recovered by an explicit status read. Rollback after either actual insertion leaves neither record nor committed authority counters. Real standalone MongoDB cannot claim success.

Normal account-erasure stop orders against saves/status through the current user and workspace guard; actual guarded erasure removes the new receipt collection together with templates. Template deletion retains the historical creation receipt. The atomic template-save transaction preserves existing campaign sequence/version/task copies, provider budgets, sender permissions and live/conditional flags. No provider or credential request occurs in this save protocol.

## Browser boundaries

Synchronous single-flight starts before context/draft/sequence preparation. The original requested campaign, active campaign, editor step, token and mount fence every dependent preparation boundary. The draft helper checks before applying returned identity state, preventing a late campaign-A response from replacing an already-loaded campaign B. The intended sequence callback is captured at click. Its optional operation guard also runs inside the actual editor save queue before transport and after responses, so queued template preparation cannot start a sequence POST after departure/account loss or publish stale completion callbacks. Existing ordinary autosave callers retain their prior behavior.

The hook retains only original request/scope/input-hash references after POST. No graph is retained for replay, and status never silently substitutes current content. Unknown state disables another template save. References/holds remain memory-only: reload, unmount, browser loss or another tab can lose this recovery reference; there is no session-storage recovery, cross-tab coordination, durable browser operation history or cancellation protocol. A request already submitted cannot be recalled. Preparatory campaign/draft/sequence writes are separate transactions with their existing unknown-outcome limits; the new atomic receipt covers template creation only.

## Remaining scope and rollout

The participating new protocol coordinates original saves and normal erasure; it does not claim global exactly-once creation, authenticated source completeness or restore reconciliation. Raw/global user/UID/template/receipt writers, old nonparticipating clients, deletion of receipts outside the protocol and restoration of older database state remain outside its retained-receipt guarantee. Existing tombstone/last-check/commit-acknowledgement limits continue. Drain old API/template writers and preserve v2.72/v2.73 scheduler/worker and legacy-job cutover requirements before a later authorized release.
