## Mutation contract

The internal [capture hook](/Users/shubham/Documents/Workspace/SocialEntangler/app/outreach/core/template_mutation_snapshots.py) runs in the existing caller-owned workspace guard transaction after literal source mutation and exact BSON/checkpoint verification, before any recoverable receipt. It starts no nested transaction and writes no index, execution permission or new receipt schema.

- Legacy and recoverable creation capture encrypted metadata and graph content at the actual created revision 1.
- Legacy and recoverable metadata/graph edits capture both kinds at the original reviewed revision and the verified successor. An exact retained snapshot is validated and preserved byte-for-byte, including original ciphertext and attribution.
- Both reviewed deletion aliases and recoverable deletion share the same helper. It captures the pre-delete content against the ordinary checkpoint, in the transaction that also records the same-revision deletion terminal and optional receipt. The terminal is not another content revision. Revision 0 and the final JavaScript-safe native Int64 revision are supported without incrementing deletion's revision.

Each hook rechecks strict current actor/UID/workspace access in the owning active session, the final live source or deletion absence, full retained checkpoint lineage, exact native identity/revision/full-record digest, and both snapshot collections. The mutation callers retain their existing permission and authority-counter fences. Source/checkpoints, both encrypted kinds, optional receipt and transactional authority changes commit or roll back together. Ordinary authentication hydration can still write outside this transaction, as before; tests distinguish it from guarded authority writes.

The existing codecs, ciphertext schema, strict context binding, graph field policy and public operation receipts are unchanged. Existing source templates remain plaintext; allowlisted free text may itself contain sensitive information. This adds neither key management nor cryptographic erasure, WORM storage, an authority outside backups, execution authorization or a complete BSON backup.

## Rollout, recovery and retention

`OUTREACH_TEMPLATE_SNAPSHOTS_ENABLED` defaults to the exact string `false`; exact `true` opts into capture. Other values hold new mutations with a sanitized 503. Disabled hooks read no snapshot storage, indexes or key, preserving existing authoring behavior. [The environment example](/Users/shubham/Documents/Workspace/SocialEntangler/app/backend/.env.example) documents the setting but does not enable it. Current Compose mappings do not propagate this new setting: explicit container propagation is still required before any later activation. Neither Compose configuration nor a running process flag was changed here.

Before activation, separately prepare all three non-TTL history/metadata/graph indexes, verify the encryption key and backup/rotation policy, drain or replace incompatible template writers and erasure workers, and propagate coordinated configuration to every participating process. Missing/conflicting/TTL indexes, missing/wrong keys, malformed legacy content and capacity failures hold enabled new mutations. No customer/startup DDL, fallback capture, eviction, repair or silent re-encryption occurs. Index observations before/after work do not globally fence DDL; the process setting does not fence older/raw writers or make disabling/re-enabling capture gap-free. Production performance and resource rehearsal remain open.

Completed original recoverable receipts and their status reads keep precedence over current template content and the new capture prerequisites. They survive deletion and missing snapshot indexes/key, and even an invalid new capture setting. They do not replay mutations or backfill snapshots. Lost acknowledgement returns the original unconfirmed contract; explicit original status/retry confirms a committed receipt without generating new ciphertext. Legacy nonrecoverable unknown outcomes still require inspection.

Per-kind limits remain unchanged: metadata 1,000 rows, 16 KiB per row, 14,000 ASCII ciphertext characters; graph 100 rows, 128 KiB canonical content, 256 KiB per row, 190,000 ciphertext characters; each accepts at most 8 MiB retained-plus-new BSON. The integration adds a shared 8 MiB accepted retained-plus-new BSON cap across both kinds and both requested revisions. The entire batch is validated/planned before insertion. Each existing bounded loader still runs before the combined byte check; this is not a physical transfer, server-work or whole-transaction memory/runtime cap. The owning transaction retains its existing 10-second timeout. Exact existing pairs can support deletion at capacity; new revisions may hold without eviction. Unsupported legacy definitions/descriptions may also hold ordinary deletion; separately guarded account/workspace erasure still purges retained content after source deletion.

The unchanged history response continues to return `content_available=false`, `capture_complete=false`, `restore_available=false` and `execution_authorized=false`. No frontend change, public content read, viewer, restoration or complete historical capture is delivered. The next local product step is an explicitly authorized bounded content-read contract before its viewer; restore remains a separate protocol. Operational activation prerequisites and broader application/security gates remain open.
