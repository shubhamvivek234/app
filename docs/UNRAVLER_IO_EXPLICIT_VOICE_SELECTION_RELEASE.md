# Unravler.io — Explicit sender voice selection
Version: 2.64.0 | Updated: 2026-10-13 IST | Status: Local, uncommitted, undeployed

Earlier assignment could leave multiple voices attached to one sender. Binding selected the first matching record, or fell back to any workspace voice when none matched. This bounded A18 repair requires one explicit sender assignment and makes assignment transitions invalidate affected prepared/audio-review identities.

## Implemented behavior

- [Shared selection](/Users/shubham/Documents/Workspace/SocialEntangler/app/outreach/core/voice_selection.py) reads at most two strictly scoped matches. Zero or multiple matches stop preparation/review/execution with an explicit selection error. Malformed assignments, missing/currently invalid profile revisions and missing provider voice references deny. There is no workspace-first voice, mock voice fallback, implicit default or automatic ambiguous-history adoption.
- [Sequence content binding](/Users/shubham/Documents/Workspace/SocialEntangler/app/outreach/core/content_approval.py) uses this selection during initial preparation, saved-artifact validation and final submission revalidation. It preserves existing active-consent/provider-source checks and adds the selected local voice ID to the binding. Existing profile identity includes its revision and source/consent facts. Transactional authority cursors retain the selected profile fence; participating assignment/dispatch/preparation writers share the workspace guard.
- [Assignment API](/Users/shubham/Documents/Workspace/SocialEntangler/app/outreach/api/voice.py) now requires a strict integer `revision` and bounded unique sender IDs. It checks the current profile revision and exact scalar workspace/sender references. One guard transaction removes those senders from earlier voices, increments all affected profile revisions and installs the requested assignment. Each conditional write must match; failed/stale/busy/unproven requests cannot return success or partially move an assignment.
- Removal can clear revoked voice assignments without restoring consent or provider authority. New assignments still require active recorded consent and the current provider source/reference. Unfinished Studio work remains blocked. Removing the last explicit choice leaves no voice selected; selecting it again has a new revision/identity.
- [Voice Studio](/Users/shubham/Documents/Workspace/SocialEntangler/app/frontend/src/outreach/pages/OutreachVoice.js) sends the displayed revision, refreshes after confirmed success and shows conflicts instead of silently swallowing them. It explains replacement and unassignment and permits removing a revoked assignment while disabling new assignments to that voice.

## Prepared clips, rollout and boundaries

Changed selection/profile revision produces a different exact binding. Earlier artifacts and approvals remain retained evidence; they are not deleted or relabeled. Current binding validation rejects them, so they cannot authorize the new selection. Already-possible/unknown paid work retains its existing uncertainty rules and cannot be replayed by this change.

Adding `voice_selection_id` also changes older voice-note bindings even when their stored voice happened to be the same. Users must explicitly prepare/listen/review the current binding; this is not an adoption migration or automatic regeneration. The assignment client and API must be released together: older callers omitting `revision` will be rejected. The existing live/generation flags remain unchanged.

The supported choice is an explicit sender assignment, not a newly implemented campaign override/default system. Legacy malformed/orphaned profiles, source adoption/custody migrations, authenticated source evidence, actual live generation/sending and transactional restore activation remain separate work. Raw writers outside the guard/revision protocol are not covered by its concurrency guarantee.
