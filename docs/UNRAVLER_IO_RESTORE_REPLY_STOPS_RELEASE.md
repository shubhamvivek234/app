# Unravler.io v2.38 — selected sender-specific LinkedIn reply-stop restore

Date: 2026-10-09. Local, uncommitted and undeployed. Foundations through v2.22 remain at `04ca28b5d1dd7bd213ea67e951970e19fd93bdf3`; earlier local changes remain intact.

## Result and limits

A private controller now restores selected negative LinkedIn follow-up blocks lost by an older backup. It stores them separately from inbox threads and integrates them into the sequence executor's existing recipient-reply preflight, including final transactional dispatch validation. Member URN or canonical profile URL matching is scoped to the workspace and app sender ID. It creates no messages, reply history/events/KPIs, condition-branch evidence, inbox freshness, consent, credential, grant or campaign resume. Email reply-related negative blocks remain the v2.37 email suppression scope; email attribution recovery is not supplied here.

This is selected negative reconciliation, not complete or authenticated recovery. Old threads retain the app `account_id` but no frozen historical external sender identity. Export binds that app ID to its **current stored** LinkedIn mapping; it does not prove who held the account at the historical reply time. A legacy sender remap may therefore conservatively block extra follow-ups. Source and target must have the same selected app ID and current stored mapping. Missing/deleted/ambiguous senders, different mapping or unsupported identifiers deny; no automatic account adoption/remap is offered. Runtime negatives remain effective for the same app ID even if its LinkedIn mapping later changes; credential rotation alone does not invalidate an exact saved import.

Origin, completeness, historical identity and storage outside backups remain operator responsibilities. The byte digest establishes integrity of reviewed bytes, not authenticity or trust. These private artifacts contain sender IDs, recipient identities and stored reply times. They are not permission to activate a restored environment.

## Selected source and private artifact

Export requires an all-source-writer/cache drain assertion and explicitly selected original `outreach_inbox_threads._id` references: 1–100 rows, at most 100 expanded facts, at most 65,536 manifest bytes. A 24-hex reference checks both its string and native ObjectId form; ambiguity denies. Each selected thread must be non-demo, not restore-provenance marked, have `has_lead_reply=true`, a supported LinkedIn recipient URN, an existing scoped app sender, and a stored lead message with a native nonfuture timestamp. The earliest stored lead-message time is retained at UTC millisecond precision. The legacy inbox writer may have supplied a fallback time when a provider timestamp was absent; this is stored evidence, not authenticated vendor timing. A flag-only thread or trimmed history with no retained timestamped lead message needs separate review. Partial trimming cannot be detected and does not establish complete history.

Supported URNs are `member`, `person`, `fsd_profile` and `fs_miniProfile`, with bounded tokens. A present profile URL must normalize to a supported canonical LinkedIn profile URL; no arbitrary URL or email-as-URN is accepted. Each fact contains app sender ID, current sender-mapping digest, recipient field/value, stored reply time and hashed original record reference. It excludes message text, conversation payload, cookie, key and credentials. Duplicate aliases across selected threads deny rather than selecting provenance silently. Majority reads and pre/post source closure checks establish individual retained facts, not one atomic source snapshot. The drain is asserted, not detected; raw/cache and post-check/file-write races remain outside this protocol.

Strict version-1 parsing rejects duplicate/unknown JSON fields, unsupported/boolean version, mixed mappings for one sender ID, duplicates, malformed UTF-8/nonfinite values, unsupported identities, invalid/future dates and excess capacity. Immutable facts, exact-byte source digest and normalized-fact digest bind review and journaling.

The CLI reuses v2.36 private file helpers unchanged: exclusive 0600 export in an owned private directory, no overwrite, inode-owned partial cleanup, bounded stdin or owned private regular input, no symlink/hardlink and changed-read denial. It reads import material before connecting to the database. Console output contains bounded review metadata, including counts/digests and the requested workspace ID, with sanitized argument/runtime failures. It never echoes recipient identities, source thread references or manifest contents.

## Stopped transaction, runtime gate and erasure

Inspect/apply require an open tenant, matching prepared stopped v2.35 epoch and all five execution/health flags false. Apply also requires exact operator/source/evidence/review digests and an all-writer/cache drain assertion. Closed tenants deny both new imports and saved retries.

The existing workspace guard/snapshot/majority transaction fences epoch root/journal/guard, selected current sender rows and existing negative rows. Exact sender-mapping proof is checked before and after insertion. Dedicated deterministic per-workspace/sender/recipient rows use `$setOnInsert`, retaining stored dates and existing metadata. Identity/provenance collisions deny; normal authority fence counters may advance. Readback proves every selected semantic block before insertion of a permanent hashed source journal. No network/provider/key operation occurs.

Saved and concurrent retries revalidate current epoch, open tenant, selected sender mapping, original review hashes and every selected block; a journal cannot hide missing exclusions or replacement senders. Observed policy/flag changes after the final awaited step roll back all transaction writes. Commit may follow the last local check. Source drain, independently operated/raw writers, stale caches and process/fleet/kernel enforcement remain operational limits.

The new negative lookup runs before the sequence executor's legacy inbox-thread check. Member aliases and bare/www URL variants use existing lead matching. Existing negatives are read-fenced in final dispatch; the shared workspace guard orders participating inserts against authorization. A real factory-denial test and a separate guard-ordered insertion test exercise this boundary under legacy clean admission, without adding a restored positive path. This does not supply a new manual Engage/reply/email authorization policy or satisfy a reply condition branch.

Retention-first TTL removal and strict unique `(workspace_id, sender_id, field, value)` negative and `(workspace_id, execution_epoch, source_digest)` journal indexes precede cutover; duplicate semantic rows deny. Erasure purges recipient negatives/journal and keeps only minimal hashed provenance plus permanent closure. Standalone Mongo denies without fallback. Physical uncertainty/owners/tokens, credentials, budgets, assets and leases remain held and unchanged apart from ordinary authority counters.

## Private procedure

On the trusted source, identify original thread `_id` references and verify the app sender's current mapping and historical limitations. Drain writers/caches. Run `python -m outreach.ops.restore_reply_stops export --workspace WORKSPACE --thread-record ORIGINAL_THREAD_ID --output-file PRIVATE_FILE --all-writers-and-caches-drained`, repeating `--thread-record` as needed. Use an owned private directory. Independently establish source provenance and keep the artifact outside database/configuration backups; the application cannot verify that storage location.

On an isolated open target, keep all five flags false and writers/caches drained; prepare the matching stopped v2.35 epoch. Run `python -m outreach.ops.restore_reply_stops inspect --workspace WORKSPACE --manifest-file PRIVATE_FILE` (or bounded `--manifest-stdin`). Review the exact digest/counts and same existing app sender mapping. Apply the same source with `apply`, `--operator`, `--source-digest`, `--evidence-digest`, `--review-digest` and `--all-writers-and-caches-drained`. Retain the original digests for receipt retries. No recipient, cookie, UID, key, grant, activation or replay arguments are accepted. Keep execution stopped afterward.
