## Shared admission contract

The read-only [evaluator](/Users/shubham/Documents/Workspace/SocialEntangler/app/outreach/core/campaign_readiness.py) serves stored GET preflight, prospective POST preflight and [campaign launch](/Users/shubham/Documents/Workspace/SocialEntangler/app/outreach/api/campaigns.py). POST applies the same name, sender, schedule, timezone and daily-limit overrides as launch, without saving them. Responses contain sanitized advice; internal account/credential records are not serialized.

Known checks cover the open paid workspace, saved valid supported sequence and current capability flags, authorization revision/state/edit/activation ownership, positive restore admission, strict scalar tenant/sender identities, current sender status/stop/cooldown/installation state, sender slots, exact proxy asset/lease/transport binding and provider term, locally checkable stored credentials, applicable mailbox pilot/sync/refresh state, enrolled leads, valid working windows and limits, selected unfinished work and Engage warm-up. Duplicate selected sender identities, array scope aliases, retained claims without proven expiry and unfinished installation state cannot establish readiness. A missing saved sequence blocks launch; launch no longer invents a default template.

Selected holds include current campaign or selected-sender task, intent, physical, manual, email, finder and connection records, plus retained sender execution ownership/latches. Finder checks use the production `outreach_email_discoveries` family. Executed intents without completed projection repair remain held. Received evidence is not replayed, repaired or cleared by readiness. These checks are a selected current-record inventory, not a complete census of old/raw writers, erased resources or external activity.

LinkedIn and email capability policies remain distinct: an eligible email-only sequence uses its own feature/pilot/mailbox/seat checks and does not require LinkedIn cookies or the LinkedIn live-action flag. Applicable combined sequences require both routes. A stored matching proxy assignment is configuration and term evidence, not fresh physical proxy health or remote session authentication.

Default Fernet material is strictly opened locally for bounded usable cookie/JSESSION/proxy-password checks, without legacy plaintext cookie/password fallback. Scoped KMS envelope inspection validates bounded metadata, configured key/context and transport identity without unwrapping a key. Metadata inspection cannot authenticate ciphertext or prove actual IAM/key availability; a structurally valid corrupted envelope can still fail final opening. The [custody helper](/Users/shubham/Documents/Workspace/SocialEntangler/app/outreach/core/credential_custody.py) shares the same parser with final opening. No KMS/provider call is made by preflight.

Assessment has a ten-second caller deadline and bounded source reads. Sender reads allow at most the five-seat pilot; warm-up reads detect overflow rather than silently certifying truncated lists/contacts/actions/leads. Incomplete reads return blocked/unknown advice with a sanitized verification message; launch returns a retryable 503 for that case. Known invalid graphs produce a sequence blocker. Caller deadlines do not prove remote cancellation or bound all database-server work.

## Activation and execution are separate

Manual draft/paused activation, explicit resume and worker-owned automatic warm-up activation preserve their existing distinctions. Installed restore epochs stay stopped. An ordinary paused `restore_review` reason alone is revalidated through the existing manual resume path and is not treated as a new-epoch activation grant.

A valid future working window is allowed, with execution deferred. Manual launch may preserve a future Engage cooldown after all required engagement is confirmed. Automatic activation requires its exact still-owned warm-up claim, required linked list and elapsed full cooldown. Missing engagement and capacity overflow block admission.

For LinkedIn, final launch separately prepares session/proxy material outside database transactions with five-second caller timeouts and captured custody-policy checks. It then rereads the original persisted campaign and repeats shared prerequisites, comparing the captured sequence and accounts before the existing activation claim. Tested term/resource/credential/campaign/policy/hold changes during key preparation deny activation. The existing revision/lead-admission activation CAS and final worker/provider guards are retained.

These reads and activation writes are sequential. They are not a snapshot transaction across every authority, do not atomically order clock/configuration changes with activation and do not cancel a physical effect already authorized elsewhere. An advisory eligible result can later fail key opening, ownership claim or final worker validation. Preflight does not issue a grant, refresh tokens, request an inbox sync, generate voice, create approvals, probe a provider or mutate authority fences.

Exact recipient/revision-bound approval, selected voice/artifact eligibility, fresh short-lived permission, inbox/reply/suppression evidence and health remain applicable execution requirements. Some depend on sender allocation and the new campaign revision; requiring them as already satisfied before allocation would deadlock admission or certify the wrong revision. The response therefore always has `execution_ready: false` and explicit pending/unknown execution checks. This slice does not certify every lead's approvals, select a voice implicitly as a readiness proof, authenticate reply recovery or implement restore activation.

The [request hook](/Users/shubham/Documents/Workspace/SocialEntangler/app/frontend/src/outreach/hooks/useCampaignReadiness.js) binds results to the campaign, prospective inputs and current token. Refresh clears the previous green result; errors, malformed/wrong-campaign responses, newer requests, input changes and logout cannot install an old eligible result. Pending requests are aborted on replacement/unmount. This request binding is not a universal frontend workspace/role-revocation protocol.

Normal confirmation is disabled while the checklist is pending, failed or blocked. After saving the draft/sequence, normal launch requests a fresh assessment of the exact prospective payload and checks that the local context has not changed before posting launch. Explicit conditional arming retains its separate server-side contract; it is not forced through the manual activation checklist or silently enabled.
