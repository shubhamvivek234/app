# Unravler.io — durable mailbox connection and OAuth interruption fencing
Version: 2.15.0 | Updated: 2026-10-04 | Status: Local implementation; rollout and live-provider evidence pending

The fourteenth slice gives mailbox authorization a durable reference outbox, an exact worker lease, conservative exchange evidence and an atomic installation receipt. It corrects broker-loss, stale-worker, paid-expiry and disconnect paths that could previously discard ambiguous OAuth outcomes. Default custody remains `legacy_fernet`; live actions, email pilot and campaign voice generation retain their disabled configuration defaults. No commit, push, deployment, real AWS/provider call, production grant or purchase was made.

## Implemented scope

- Browser-bound OAuth state and encrypted code/PKCE consumption still commit together under the workspace guard. A queued job now records publication/recovery due times. Immediate broker failure leaves that committed encrypted job queued; it cannot reset its original ten-minute authorization deadline. Task payloads contain only job/workspace references. Separate thirty-second beat tasks publish and recover bounded sets of fifty rows.
- Publication persists a due-time claim before broker work. A lost broker acknowledgement can cause another reference to be published, but cannot authorize another token exchange. Publication and recovery have separate due times; disabled/closed tenants receive exact-owner/material/status-fenced, guard-only scheduling backoff. That control neither changes status/credentials/permission nor reopens erasure. A blocked prefix of fifty tenants cannot starve subsequent open work.
- Worker claim uses snapshot/majority workspace ordering and current paid sender/pilot/shutdown checks before opening secrets. It stores protocol v2, an exact owner, `preparing`, and a two-minute lease. Original provider/sender/code/PKCE, authorization expiry and lease are revalidated under the guard after asynchronous opening. Standalone MongoDB denies before key work or HTTP; no production fallback exists.
- Token transport commits `possible` before HTTP in the same transaction as its conservative per-sender UTC-day allowance. The pilot limit is ten possible OAuth exchanges per sender/day. Failed acknowledgement, uncertain call or even a subsequent local transport denial never refunds that allowance. Transaction retries repeat database work only; token and profile HTTP stay outside callbacks. Captured paid/code/lease deadlines and custody mode/environment/pilot/shutdown controls are checked synchronously after authorization commit and before transport.
- Timeout, cancellation, malformed response, lost permit/response acknowledgement and failure before installation cannot make an exchange automatically sendable. Lease recovery can requeue only protocol-v2 `preparing` with a still-usable original code. `possible`, `unknown` and unmarked legacy running work become `review_required`; code/PKCE are scrubbed while TTL-free metadata remains. Explicit received HTTP 400/401 OAuth error bodies may close the rejected operation, without refunding its allowance. Other failures remain conservative holds.
- Malformed access/refresh values and invalid lifetimes deny before profile HTTP. An explicit lifetime must be positive and at most 86,400 seconds; a missing value retains the existing 3,600-second default. Stored expiry starts conservatively at worker claim, so subsequent profile/key-service work cannot extend the provider's stated lifetime. No minimum sixty-second extension is added for shorter grants.
- Successful installation stores encrypted mailbox credentials and the job's metadata receipt atomically. The receipt records owner, generation, material digest and installation time, and scrubs code/PKCE. Installation rechecks current job/material, paid controls, lease/deadline and the exact prior mailbox snapshot; KMS stays outside the transaction. A lost installation acknowledgement preserves the committed credentials/receipt and returns the completed local installation without another exchange. A stale owner cannot remove replacement material.
- Inbox initialization/catch-up is now independent of OAuth completion. New mailboxes remain `initializing`; reconnects preserve the existing history/delta cursor and remain `reconnecting`. Existing periodic polling can initialize or catch up later, and healthy/fresh reply coverage still gates email. Sync failure no longer discards an already committed installation. This change does not supply a durable sync HTTP outbox, physical-read budget or universal cursor/transport recovery.
- Disconnect and paid-expiry cleanup share the held-state-preserving job stop. Both participate in workspace ordering. Paid mailbox cleanup fences the expired entitlement and deletes only bounded captured OAuth-state rows in that same successful transaction; renewal cannot cause a newly created state to be deleted by the old mailbox stop. Broader paid-expiry cleanup retains its existing separate transitions. Pending/proven unused work can fail; ambiguous exchanges retain the review slot even after payment reactivation. Provider custody migration treats that review slot as unfinished work. Settings polling stops on review and displays an operator-review reason.
- Erasure includes the exchange-budget collection, scrubs code/PKCE and retains only minimal hash/kind/state evidence for unresolved exchanges and installed receipts. It preserves no bearer values, mailbox address, PKCE/code ciphertext or worker owner in the hold. Installed receipt evidence is distinct from a remotely revoked OAuth grant or verified email delivery.

## Index cutover and operator constraints

Drain all old/new API, OAuth, mailbox/refresh/sync, publishers/recovery, paid/erasure and credential/transport writers and their caches before first cutover. Verify the actual deployment supports snapshot/majority transactions. The startup index routine now secures mailbox retention before any other index builds: remove existing connection-job TTL indexes, quarantine ambiguous/unmarked running work, then build the strict expanded unique workspace/sender active slot covering `pending`, `queued`, `running` and `review_required`, plus separate due indexes and the budget index. Browser-state TTL remains; job metadata has no TTL.

Retention removal succeeds before lengthy or failing uniqueness validation. Duplicate review slots or index conflicts propagate failure and block cutover; they are not ignored. Existing historical duplicates need separate drained review, not deletion to make the index pass. After successful cutover, routine repeated startup does not quarantine live v2 exchanges. Mongo's TTL monitor continues even when application workers are drained; records already removed by a prior TTL cannot be reconstructed by this migration. MongoDB's [partial-index documentation](https://www.mongodb.com/docs/manual/core/index-partial/) describes the underlying unique-filter semantics; actual old/new index coexistence and duplicate denial were tested locally.

Never reset `possible`/`unknown` to queued or delete a review row to reconnect. This slice deliberately does not introduce an operator command that resolves an OAuth hold or reconstructs an unsaved token response. Existing manual-action/LinkedIn-connection repair commands do not prove an OAuth outcome. A separate drained OAuth review/stop protocol and provider-side revocation evidence are needed where appropriate. A saved installation receipt proves that local transaction, not delivery, provider revocation or freshness.
