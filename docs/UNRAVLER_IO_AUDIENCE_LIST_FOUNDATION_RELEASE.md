# Unravler.io v2.67 — Campaign audience-list foundation

Updated: 2026-10-14 IST. Local F1 backend foundation; uncommitted and undeployed. The list-management UI and import-to-list binding remain F2.

## Result

Campaigns can have named audience lists that reference existing campaign lead records. One enrollment can belong to several lists, with no duplicate enrollment, sequence job or send path. These lists organize contacts; adding/removing membership, renaming or archiving a list does not launch, pause or delete an enrollment. Existing campaign controls still determine execution.

This slice adds the backend contracts and guarded metadata lifecycle. It does not collect a new source, bind import jobs to lists, create a customer UI or activate search collection. F0 search-source holds remain intact, including when an unverified contact appears in an organizational list.

## Identity and lifecycle

`outreach_lead_lists` stores an immutable request-derived list ID, scalar workspace/campaign identity, original native campaign digest, display/normalized name, current revision, creation actor/timestamps and conservative source metadata. F1 only permits manual/not-collected or explicitly unknown legacy provenance; source fingerprint and requested source quantity remain null. Every public list response reports collection unverified.

`outreach_lead_list_members` stores one workspace/list/enrollment relation with a deterministic ID, native list-parent digest and native lead digest. BSON type differences remain distinct. A campaign, list or lead with a new native identity cannot inherit the old relationship through a reused public ID. Duplicate/malformed identities require review, rather than choosing the first matching record. Members of a different campaign or ambiguous tenant scope cannot be attached. These are stored identity fences, not authenticated backup/restore-incarnation proof.

Creation uses a bounded request UUID and stable workspace/campaign identity. Retrying the same content returns the current list, preserving later changes; reusing the request for different creation content conflicts. Names normalize consistently with a 60-character limit and remain unique within a campaign, including archived lists. Campaigns cap at 50 lists. Rename/archive/member edits require the current positive integer revision. A stale or acknowledgement-lost mutation requires rereading the current list/membership before retrying; it cannot silently advance another revision or duplicate a relation.

Every write uses the existing workspace suppression guard and snapshot/majority transaction. The current parent is reread and physically touched so a concurrent deletion or conditional warm-up conflicts and is revalidated. No lead, sender, campaign authorization, sequence or job is modified; the parent only gains `audience_metadata_revision`. Standalone Mongo cannot partially persist the change. Requests cap at 100 distinct contacts; selected leads and existing memberships are fetched in bounded batches with exact public/native identity checks, then necessary writes commit together.

Membership reads page by deterministic ID, at most 100 records, and batch-hydrate current scoped lead references. Deleted/replaced/moved contacts appear as orphaned with no contact payload; retained search markers appear as source review. The `available` status only means that the same native campaign contact reference is present; it does not assess reply/DNC, paid term, sender, schedule, launch or execution eligibility. `membership_count` counts stored relations, not verified audience, approved leads, future sends or provider completeness. Concurrent membership changes are not a snapshot/completeness guarantee, and a fresh enumeration is needed after changes. Archiving/removing a list does not stop outreach; F2 must make that distinction clear in its customer controls.

## Existing audience backfill and retention

An explicit admin-only endpoint creates one deterministic “Existing audience” list per known campaign and adopts at most 100 existing records per call. It requires a drained-enrollment-writer assertion and a current revision (0 initially), captures a scalar-public-ID upper bound, and resumes its checkpoint transactionally. Lost acknowledgement plus stale revision cannot move the next page. Malformed or duplicate contact identities and inconsistent checkpoints deny without partial writes in that batch; earlier committed pages remain retained.

The response says `selected_scope_complete` only for its captured scalar workspace/campaign/ID scope under the drain assertion; it never proves an authenticated full audience or complete collection. The assertion is not measured fleet-drain proof. Orphan campaigns and array/unknown scope records are not reparented or adopted. Historical source remains `legacy_unknown`. Existing leads, source markers, sequence bindings, tasks and authorizations stay unchanged. `processed_count` is the checkpoint's historical processed rows, distinct from the current membership count after later organizational edits. New records outside the captured bound need a later deliberate workflow, not an inferred full-history claim.

Required unique indexes cover workspace/list identity, campaign normalized names, and list/enrollment membership. The membership page lookup, workspace/public-lead batch lookup and workspace/campaign/public-lead ordered backfill have supporting indexes; the latter lead indexes deliberately remain nonunique so historical ambiguity is reviewed instead of removed. Index conflicts fail startup and require drained review. No conflict is deleted or silently adopted. There is no automatic production backfill.

Campaign deletion hides list reads through the deleted parent while retaining metadata for the existing soft-restore lifecycle. Lead deletion leaves an orphan reference with no copied contact details or identity adoption. Both new collections join the existing workspace-erasure inventory; its actual guarded erasure batch removes current-tenant records while preserving another tenant. Whole-product/legal/backup retention remains outside this slice.

## API and verification

The seven `/outreach/lead-lists` handlers use the same resolved permission and erasure admission as other outreach endpoints. Reads require `lead:read`; create requires `lead:create`; rename/membership require `lead:update`; archive requires `lead:delete`; legacy adoption requires `workspace:update`. Strict request models forbid source/execution overrides and coercible revision/drain values.

- Final focused verification: 72 passed with zero skips, comprising 21 contract checks and 51 actual MongoDB/HTTP cases. Combined statement coverage is 92% (`lead_lists` core91%, API100%). The native winning query plan uses an index scan without a blocking sort for the captured audience range.
- Fresh broader outreach regression: 3,046 passed, 1,382 historical/opt-in skips, two warnings, 124.02 seconds.
