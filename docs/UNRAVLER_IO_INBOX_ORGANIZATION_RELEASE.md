# Unravler.io — Inbox organization
Version: 2.73.0 | Updated: 2026-10-16 IST | Status: Local verified implementation; independently reviewed

The inbox now supports workspace-shared stars, archive/restore and one editable plain-text conversation note. Inbox, Starred (unarchived only), Archived and All views combine with existing sender, source, search and lead-tag filters. The UI defaults to Inbox; an omitted API view remains All for older callers. Archive changes organization only: it never stops/restarts a campaign, clears reply/DNC/opt-out, changes permission, deletes a conversation or creates provider work. New messages retain the archived status until a user explicitly restores it.

## Identity, authority and edits

The existing thread stores optional `inbox_organization` metadata: revision, exact boolean flags, note and last-update actor/time. No new collection/index exists. Absence means revision zero/unstarred/unarchived/empty note. Malformed/unknown schema, audit fields or unproven identity disable controls for review. Native BSON identity plus exact workspace/public thread/sender/optional LinkedIn channel/conversation/person context and canonical revision/flag/note content bind the review digest; the final CAS also captures the whole raw organization object, including audit fields. Digests are references, not secrets or external-provider proof.

`PATCH /inbox/{thread_id}/organization` requires `inbox:manage`, strict current revision and review digest, and only explicitly supplied star/archive/note changes. Notes allow 4,000 Unicode code points, ordinary line breaks/tabs and explicit empty clearing; other controls/surrogates deny. BSON Int64 revisions are converted within the exact JavaScript integer bound; bool/fraction/string revisions deny. Same-revision competitors have one winner. Replaced native IDs, sender/recipient context, raw metadata and duplicate public IDs deny. This PATCH does not modify message/reply `thread_revision`, messages, unread count, suppression or campaign state.

One workspace-guard/snapshot/majority transaction validates open workspace and the admitted actor's original bounded scalar Firebase UID, and fences current user/member-or-owner records before the whole-organization CAS. Missing/deleted/replaced auth identities, tombstones, removed/downgraded/ambiguous membership and erasure deny. Metadata fence counters on existing authorities/guard are the only side effects outside the thread. Standalone transactions deny. Raw/older writers, independently inserted tombstones outside participating ordering and last-local-check/commit timing remain limits; no new per-sender team grants or workspace read policy is introduced.

## Views and browser behavior

Filtered views project at most 1,001 matching identity/organization rows. Over 1,000 candidates explicitly requires narrower sender/search/tag filters, with no partial page. One strict public schema classifies rows: malformed organization stays visible in Inbox/All for review rather than masquerading as Starred/Archived. Full bodies load only for the page. The body query reapplies original filters and compares raw BSON identity/organization presence and values, including malformed rows; changed/deleted/nonmatching page rows return a reload conflict. Sequential reads are not a snapshot/completeness/strict byte bound. Legacy metadata size and server-side matching/sort cost remain separate. All retains legacy pagination.

Browser success requires the matching thread/native identity, exact next revision and all requested returned fields. Unknown/failed/contradictory responses preserve notes and hold further organization writes until reload; original revision prevents applying a committed edit twice. There is no request ledger/automatic replay. Reload uses the existing conversation GET, which resets unread count; it does not repeat the PATCH and is not database-read-only.

Drafts stay separate per native identity through recipient and empty-view switches, cap at 50 unsaved identities, remain memory-only and clear on unmount/page reload. No note text enters browser storage. Exact edit generations preserve newer edits even when text returns to the submitted value. Stale drafts do not become current after unrelated star/archive saves; users explicitly review the latest version or choose saved text. List/detail/save responses never replace a newer same-identity organization revision. Local entry conservatively caps 4,000 UTF-16 units; server projection validates 4,000 code points. Notes are ordinary shared workspace data, not encrypted credential custody, personal notes or immutable history.

## Compatibility and recovery

Actual current inbox synchronization preserves organization while updating message fields. An archived recorded reply still satisfies the actual sequence recipient-reply suppression helper. Existing guarded workspace erasure purges the same thread, with a native stop/inspect/finish check proving no note survives in minimal holds. This is not complete cross-enrollment suppression, authenticated reply completeness, whole-product/backup erasure or live provider proof.

No backfill/restamping is introduced. Older clients retain list/detail/reply compatibility. A future coordinated release must replace current backend/UI versions and assess/drain older sync writers; current-source regression does not prove older binaries. Earlier v2.72 source and stricter scheduler/worker cutover remain intact and local. Live/conditional flags stay disabled.
