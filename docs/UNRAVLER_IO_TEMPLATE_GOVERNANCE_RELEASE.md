## What changes

Custom-template deletion requires a review of the exact stored native record. The gallery obtains read-only metadata, submits the captured review and removes a displayed row only after HTTP200 with the exact matching deletion receipt. Missing, changed, malformed, ambiguous, unsupported or cross-scope reviews cannot delete a replacement record. Existing campaign sequences, immutable campaign versions, leads, tasks, suppression and provider/execution permissions are unchanged.

The browser uses `DELETE /sequences/templates/{id}/reviewed`. An older API exposing only the old single-ID route returns404 for this extra path segment and cannot silently ignore the new body. The new API also retains the old URL with the same mandatory review/body/authority checks; an old unreviewed request receives422. Read metadata without the new contract leaves deletion unavailable. Neither a review nor its digest is a deletion/execution grant or a signed external receipt.

## Native record and current authority

Review recognizes current custom IDs (`tpl_custom_` plus ten lowercase hex characters), a supported scalar native ObjectId or nonblank bounded string, exact scalar workspace and creator, strict custom marker and JavaScript-safe integer revision. Existing absence means revision0; new saves begin at1. No bulk restamping, migration, template-history collection or new index is introduced. Unsupported older identities/revisions remain held for separate reviewed repair. This is an optimistic review contract, not a new immutable template revision history or time-limited content approval.

The full received BSON record is fingerprinted, including native numeric representation, revision presence, creator, graph and unknown fields. The identity digest separately binds native/public/workspace identity; a scope digest binds the originally admitted actor, scalar Firebase UID and resolved workspace. Strict request fields forbid coercion and unknown keys. The accepted full BSON record is at most1MB, after loading/encoding; the limit includes compiled/copy metadata and can reject a graph that fits the separate authoring bound. It is not a database-read/HTTP-ingress memory bound. Malformed or oversized BSON stays unavailable.

Deletion uses one shared workspace guard with snapshot/majority transaction semantics. It rechecks the current unique native user and original UID, current member permission or unique workspace-owner authority, active status, identity-erasure tombstone and open workspace. A bounded UID lookup includes array aliases and denies another public user ID with the same UID. Native authority-counter writes conflict with changes to the user/member/owner records used for authorization. Owner fallback requires one scalar workspace record before checking its owner; a second workspace record with another owner cannot be ignored. Existing workspace roles govern shared templates; this adds no creator-only override, team/sender ownership or new role.

Within that same transaction, a bounded unique scoped lookup rechecks the original template identity, revision and full-record digest. A copied `$literal` full-row CAS removes that native row. Literal operator-looking stored values cannot become query operators. Mongo object equality is not strict BSON-byte equality; the digest reread and same-document transaction conflicts supply the tested protection against content/native replacement during authorization. Review metadata is not continuous read authorization or a complete catalog snapshot.

New template POST writes now participate in the same guard and current sequence:create authority, coordinating insertion with deletion/erasure. Existing compiler/semantic/visual-source checks remain. Public/native IDs are prepared once per server request and stay stable on definitely aborted database retries; collisions deny instead of overwriting. This does not add durable client-request idempotency or save recovery: an uncertain save may have committed, and a later manual retry can create another template. Template editing/sharing, durable operation receipts and immutable template history remain subsequent work.

## Unknown outcomes and browser behavior

Only the exact HTTP200 receipt confirms the requested deletion: contract version, template ID, workspace, original revision, identity/full-record/scope digests and deleted status must all match. HTTP201/202, malformed/extra/authority-claiming bodies, missing acknowledgements,403/404/409 and failed transports retain an unconfirmed hold. Unknown commits are not automatically replayed. A second attempt using a known deleted review returns404; that is not reconstructed proof of the original outcome.

Single-flight controls block overlapping deletion and template Use. Mount/view-generation checks and current-row metadata comparison prevent a stale receipt from removing a replacement view or showing a success message after departure. Explicit **Reload and review templates** performs only GET. An absent row in the existing capped catalog is not a deletion receipt, and the unconfirmed notice remains visible. A successful explicit refresh permits a new deliberate deletion using the refreshed review; it never resends the earlier request automatically. Failed refresh retains the hold, including competing Retry/refresh events.

The hold and one current notice are memory-only. Reload/unmount loses that client state, and a later deliberate operation can replace the earlier notice. This is not durable deletion-outcome history, cross-tab coordination or authenticated completeness. A request accepted before departure cannot be recalled. The existing100-row custom catalog cap remains. Invalid graphs can still be deleted when native deletion review is valid; configuration eligibility and deletion permission remain independent. A viewer can receive read-only review metadata without current deletion authority; the mutation rechecks the actual permission.

## Limits and rollout

All participating new template creates/deletes and existing guarded workspace erasure share the workspace guard. Older/raw template writers and global user/UID insertions outside that protocol can introduce predicate phantoms; bounded snapshot reads do not prove commit-time global uniqueness or authenticated completeness. No new global unique index is claimed. The ordinary account-erasure entry stops the user before its tombstone/workspace stop; the native user-write conflict orders against that path. A raw tombstone insertion after the snapshot/last check is not an independent global serialization guarantee. Commit-acknowledgement uncertainty remains explicitly held.

Before deployment, replace/drain old API/template writers so POST insertion participates consistently, then release the browser against the guarded API. The reviewed URL prevents the older DELETE-handler fallback; it does not make arbitrary mixed old writers safe. Preserve the earlier v2.72/v2.73 scheduler/worker drain and legacy-job cutover requirements. There is no automatic legacy adoption, campaign reauthorization or resumption.
